## 1. 背景

### 1.1 课程与案例

- **课程目标**：让传统研发掌握「从模糊需求到真实项目上线」的 AI 全流程开发方法（需求澄清 → PRD → 设计 → 开发 → 测试 → 部署验收）。方法论全文见 [`ai-fullstack-dev-training.md`](ai-fullstack-dev-training.md)。

## 2. 待评审的核心矛盾（问题陈述）

> **学员从同一段模糊需求出发，做出来的系统必然各不相同**——表结构、API 路径、页面、甚至技术栈都不同。**但课程需要客观验证「做出来的东西对不对」**。最自然的直觉是接口验证：调用学员系统的接口、比对返回。可是学员的接口互不相同，统一接口验证不可能。又要验证、又无法统一验证面，怎么办？

### 2.1 解法：分层——验「钱的口径」，不验「实现的样子」

把「验证什么」和「允许不一样什么」切开：

| 层 | 内容 | 验证方式 | 理由 |
|---|---|---|---|
| **收敛层** | 业务规则的结果数字：提成阶梯、四级工资公式、跨月顺延、业绩归属、流水唯一性、回款超额拦截 | **自动验收**：客观、有唯一正确答案 | 钱没有第二种「对法」 |
| **发散层** | 表结构、API 设计、状态机建模、页面、代码组织 | **人工评审 / 学员互评** | 发散本身是教学素材（架构对比比表名对比有价值得多） |
| **判据** | 凡是发现「没法自动验证」的东西，属于评审，不进验收 | — | 验证器只裁客观，人裁主观 |

验收器对学员系统只说一句话：**「给定同样的业务局面，你的系统算出来的数必须和口径一致。」** 它从不说「你的系统应该长这样」。

### 2.2 约束包三件套

给学员的模糊需求之外，加三类约束（模糊的是「做什么功能、怎么实现」，确定的是「业务背景、输入数据、可验证的结果」）：

1. **背景包**：业务背景说明（这门生意怎么转、痛点长什么样）+ 统一口径基准（F1–F12 / D1–D7 作为参考答案与验收对齐基准）。
2. **输入包**：统一上游接口（lead-source-mock 外呼记录）+ 统一验收剧本（105 事件序列导出为确定性场景）。
3. **观测包（缺失的一块，本方案要新建）**：最小统一验收契约——学员内部实现自由，但必须提供一层**薄适配**，把标准「场景动作」映射到自己系统。

### 2.3 观测包的候选形态

- **形态 A｜HTTP 能力 + 映射文件**：规定约 10 个验收动作（录一单、查当日汇总、算某人月工资、推进一个工作日、审一单……），路径学员自定，交一份 `adapter.yaml` 声明「场景动作 → 我的系统调用」。验收器读映射执行。
- **形态 B｜MCP 工具集契约**：要求学员系统暴露统一命名的 MCP 工具（`record_order` / `get_daily_commission` / `get_monthly_salary` / `advance_day` …）。仓库已有完整 MCP 基础设施与授权体系，AI 助理可直接对任何学员系统跑同一套验收脚本。

### 2.4 先例证明可行性

GOLDEN.md 的双引擎差分协议已经解过一次这道题：**同一份场景数据喂不同实现，比业务结果，不比实现路径**。本方案 = 把「2 个引擎互验」泛化为「N 个学员实现互验」：剧本统一（输入包）、期望值统一（金标准）、观测面统一（观测包）、中间实现完全自由。

### 2.5 评分结构（随分层自然产生）

自动验收通过（口径正确）+ 架构评审（设计质量）+ 答辩讲清「为什么这么算」（真实理解）。

## 3. 实施路径（若方案成立）

1. 把 08 演练的 105 事件剧本导出为**实现无关的场景 DSL**（动作 + 期望数字，期望值取自 831 项核对）；
2. 定稿观测包契约（A/B 二选一）并写成《学员验收契约》规范；
3. 验收 runner 复用现有 `app/verification/` 体系，替换驱动后端；
4. 学员交付物 = 自己的系统 + 薄适配声明。适配层能跑通本身就证明其系统可表达全部必需的业务观测。

## 4. 开放问题（请评审人逐条给出倾向）

| # | 问题 | 张力 |
|---|---|---|
| Q1 | 观测包选形态 A（HTTP+映射）还是 B（MCP 工具集）？ | A 更低门槛、更普适；B 与仓库基础设施一致、对 AI 助理友好，但要求学员理解 MCP |
| Q2 | 自动验收范围只锁「钱路径」是否足够？线索五态、等级状态机这类非资金规则要不要进自动验收？ | 锁得少→口径覆盖不足；锁得多→约束过强、发散空间被压缩 |
| Q3 | 防作弊：适配层可能硬编码返回假数字。现有「1 元故障注入」思路能否延伸为「验收器注入计划外事件，要求系统实时反应」？ | 静态场景可被过拟合；动态注入提高成本但复杂度上升 |
| Q4 | 适配层的撰写成本对传统研发学员是否过重？是否应明确「AI 辅助生成为主、人工审核为辅」？ | 适配成本太高会挤占需求澄清与设计的教学时间 |
| Q5 | 口径基准（01 事实清单 = 参考答案）何时对学员公开？验收前公开会让澄清练习失效；完全不公开可能导致口径走偏、大面积返工 | 教学节奏与公平性 |
| Q6 | 固定剧本（105 事件）会被针对性硬编码。是否需要隐藏变体 / 多套随机种子？ | 与 Q3 同源：确定性带来可验证性，也带来过拟合 |
| Q7 | 模糊度控制：原始口述 + 背景包给完后，学员的澄清空间还剩多少？过模糊全员跑偏无法验收，过清晰澄清练习失效 | 案例设计的核心尺度 |
