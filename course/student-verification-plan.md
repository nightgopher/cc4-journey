# 学员自验方案：实现自由，口径统一

> **本文档是什么**：课程方的设计方案，回答「学员从同一段模糊需求做出各不相同的系统，如何让学员自己客观验证做得对不对」。
>
> **前提**：核心资金规则（提成、工资、额度、归属、回款、发放）**直接给学员**，不作为澄清考点藏起来。验证目标是让学员能自验，而不是考学员能不能猜到规则。
>
> 相关材料：评审请求 [acceptance-contract-proposal.md](acceptance-contract-proposal.md)、业务背景包 [business-background.md](business-background.md)、金标准 [../app/test/golden/GOLDEN.md](../app/test/golden/GOLDEN.md)、讲师系统验收包 [../app/verification/](../app/verification/)。

---

## 0. 一句话

**同一份规则卡 + 同一份剧本 + 学员自写的一层薄适配，统一验收器跑出按规则编号定位的报告。**

验收器对学员系统只说一句话：「给定同样的业务局面，你算出来的数必须和规则一致。」它从不规定表结构、API 路径、页面或技术栈。

## 1. 要解决的缺口

现有 `app/verification/verify.py` 很完整（16 阶段、831 项核对、1 元故障注入），但它跑的是**讲师自己的 Go 代码和测试**：Go race/vet、讲师的 HTTP 集成测试、讲师的迁移、讲师的前端构建。学员一旦换表结构、换 API、换技术栈，这套就无法复用。

因此需要新建的是一个**与实现无关的验收器**，复用现有资产的「剧本、期望值、报告与防伪思路」，替换掉「驱动后端」。

## 2. 学员拿到的四件东西

| # | 交付物 | 内容 | 发放时机 |
|---|---|---|---|
| ① | 规则卡 | 资金规则逐条写死，编号 R01–R20（见 §3） | 需求阶段，随背景包 |
| ② | 验收契约 | 约 15 个业务动作的 JSON Schema（见 §4） | **设计阶段，开发前** |
| ③ | 剧本包 | L1/L2/L3 三层场景，每个期望值标规则编号（见 §5） | 开发阶段 |
| ④ | 验收器 | `python3 accept.py --adapter http://localhost:9000`（见 §6） | 开发阶段 |

### 3.2 刻意保留的「待裁决口径」

规则卡中保留 3–4 条**不给答案**、标记为「需向业务方确认」的口径，直接取自仓库已有裁决项：

| 编号 | 口径 | 可选答案 |
|---|---|---|
| D1 | B 级额度：跨月续领 vs 每月重置 | `carry_over` / `monthly_reset` |
| D4 | A 级零业绩：降级 vs 保持 | `demote` / `keep` |
| D6 | C 级淘汰时点：第 6 天结束 vs 第 7 天检查 | `end_of_day6` / `after_day6` |

学员通过澄清得到答案后，在适配声明里写明自己的裁决；验收器按声明选择对应期望分支。**澄清仍有分量，验收仍然客观。**

### 3.3 澄清的重心

规则给了之后，需求澄清转向：

- **角色与权限**：谁能录单、谁审核、主管能看什么；
- **流程**：客户如何分配与转移、晋升谁发起谁批准、工资谁发；
- **范围**：做哪些模块、哪些不做（不做的动作在适配层声明 `UNSUPPORTED`）；
- **待裁决口径**：§3.2 的条目。

## 4. 验收契约

### 4.1 唯一入口

学员只实现一个 HTTP 入口（语言、框架不限）：

```
POST /acceptance/act
Content-Type: application/json

{"action": "record_order", "args": {"emp": "E03", "customer": "C17", "amount": 99, "date": "2026-10-12"}}
```

响应只有三种：

```
{"ok": true,  "id": "<学员系统内部ID>", "result": {...}}
{"ok": false, "error": "REJECTED"}       // 业务拒绝：超收、重复审批、重复发放……
{"ok": false, "error": "UNSUPPORTED"}    // 本系统未实现该功能
```

不规定 HTTP 状态码、错误文案、鉴权方式（适配层内部自行处理登录）。

### 4.2 动作清单

| 类型 | 动作 | 关键参数 |
|---|---|---|
| 准备 | `reset` | — |
| | `set_workdays` | month, dates[] |
| | `hire` / `leave` | emp, team, level, date |
| 业务事件 | `record_order` | emp, customer, amount, date |
| | `approve_order` / `reject_order` / `delete_order` | order, date |
| | `transfer_customer` | customer, to, date |
| | `promote` | emp, level, date |
| | `record_attendance` / `approve_leave` | emp, date, status |
| | `create_receivable` / `receive_payment` | receivable, amount, date |
| | `pay_salary` / `revoke_salary` | emp, month |
| | `record_expense` | amount, date |
| 观测 | `get_daily_commission` | emp, date |
| | `get_salary` | emp, month → 返回分项明细（固定/底薪/全勤/绩效/提成） |
| | `get_revenue` | scope(emp/team/all), from, to |
| | `get_receivable_balance` | receivable |
| | `get_ledger` | from, to → 流入、流出、净额 |

动作只用「现实世界发生了什么」描述，观测只问结果，不带任何规则参数（如不出现 `level_change_date`）。

### 4.3 三个降低接入成本的设计

1. **业务日期显式传参，不做 `advance_day`**。学员系统无需改造时钟，只要订单、考勤等记录本身带业务日期——这本来就是正常需求。
2. **ID 映射由验收器维护**。学员返回自己的 ID，验收器记录「剧本 O17 ↔ 学员 8823」，后续调用自动替换。适配层因此可以**完全无状态**。
3. **结果只分成功 / 拒绝 / 不支持**。不绑定任何 HTTP 风格。

### 4.4 适配声明

```yaml
# adapter.yaml
endpoint: http://localhost:9000/acceptance/act
decisions:          # §3.2 待裁决口径
  D1: carry_over
  D4: keep
  D6: end_of_day6
unsupported:        # 未实现功能，不计分、不报错
  - record_expense
```

### 4.5 适配层的边界

- 适配层只做**翻译**：动作映射、字段改名、登录。
- 适配层**不得做业务计算**；架构评审中「适配层含业务计算」为一票否决项。
- 预期规模 200–300 行，推荐 AI 生成、人工审核。

## 5. 剧本包

### 5.1 三层结构

| 层 | 来源 | 规模 | 用途 |
|---|---|---|---|
| **L1 规则单测** | GOLDEN G01–G15 泛化 | 每条规则 2–5 个小场景，约 50 个 | 开发某条规则时即跑，TDD |
| **L2 业务流程** | CASES V03–V12 改写 | 约 10 条链路 | 模块联调 |
| **L3 连续经营** | `journey/08` 105 事件导出 | 7 日、12 人、831 项核对 | 交付前全量 |

### 5.2 场景格式（示意）

```yaml
id: L2-RECV-01
rules: [R08]
steps:
  - act: create_receivable  {ref: RV1, amount: 100, date: 2026-10-12}
  - act: receive_payment    {receivable: RV1, amount: 30, date: 2026-10-12}
  - expect: get_receivable_balance {receivable: RV1} == 70
  - act: receive_payment    {receivable: RV1, amount: 71, date: 2026-10-13}
    expect_error: REJECTED
  - expect: get_receivable_balance {receivable: RV1} == 70
  - act: receive_payment    {receivable: RV1, amount: 70, date: 2026-10-13}
  - expect: get_receivable_balance {receivable: RV1} == 0
```

依赖待裁决口径的期望值写成分支：

```yaml
  - expect: get_salary {emp: E05, month: 2026-11}.fixed
    by_decision:
      D1: {carry_over: 264, monthly_reset: 528}
```

### 5.3 期望值来源

不手写。讲师系统写一份**参考适配**，跑剧本产出结果，与 GOLDEN 规则交叉核对一致后冻结为期望值。参考适配跑通本身即证明剧本自洽、契约可表达全部必需观测。

## 6. 验收器

### 6.1 执行流程

1. **契约冒烟**：最小剧本确认适配层连通、响应格式正确。失败时报「契约未接好」，不与规则错误混报。
2. **逐层执行**：L1 → L2 → L3，可用 `--layer L1 --rule R04` 只跑一部分。
3. **写入后回读**：每个业务事件后用观测动作回读独立比较，不以「接口成功」作为正确（沿用 CASES「为什么不是接口 200 就算正确」）。
4. **生成报告**：`REPORT.md` + `summary.json`。

### 6.2 报告按规则定位

```
✗ R04 B级额度跨月续领   L1-B03   期望 11月 264   实际 528
  提示：6 个工作日是总额度，不是每月 6 天（规则卡 R04；你的裁决 D1=carry_over）
✓ R01 日提成阶梯        12/12
✓ R08 回款不得超收       5/5
– record_expense        UNSUPPORTED（未计分）
总计：规则 18/20 通过；L1 48/50，L2 9/10，L3 812/831
```

### 6.3 防自欺

| 手段 | 防什么 |
|---|---|
| 剧本中途**重启适配进程** | 适配层自建影子账本 |
| 静态扫描适配代码中的规则常量（88、2200、30…）并告警 | 业务计算写进适配层 |
| 验收器自检反例：某个期望值改动 1 元，必须报失败 | 验收器本身失效（沿用 V12 思路） |
| 报告记录 commit 与 dirty 标记 | 交付物与运行代码不一致（沿用现有 summary.json） |

## 7. 学员自验与讲师评分的分工

| 环节 | 谁 | 内容 |
|---|---|---|
| 自验 | 学员 | L1–L3 全部公开，随时反复跑，目标全绿 |
| 隐藏验收 | 讲师 | 用隐藏种子生成 L3 变体（金额、日期、转移时机不同），期望值由参考系统现算；针对公开剧本硬编码会失败 |
| 架构评审 | 讲师 / 互评 | 表设计、API 设计、状态机建模、页面、适配层是否够薄 |
| 答辩 | 学员 | 讲清「为什么这么算」，以及待裁决口径的澄清过程 |

## 8. 学员时间线

| 阶段 | 拿到 | 与验收相关的动作 |
|---|---|---|
| 需求澄清 | 口述 + 背景包 + 规则卡 | 澄清角色、流程、范围、待裁决口径 |
| 设计 | 验收契约 | 确认系统支持业务日期、能返回内部 ID |
| 开发 | 剧本包 + 验收器 | 每写一条规则跑对应 L1 |
| 联调 | — | 跑 L2 |
| 交付 | — | 跑 L3，提交报告 + 适配代码 + adapter.yaml |

**关键**：契约必须在设计阶段发放。业务日期与外部 ID 两条约束如果到验收时才知道，学员会面临大改。

## 9. 课程方落地步骤与完成标准

| 步 | 内容 | 完成标准 |
|---|---|---|
| 1 | 写规则卡 | R01–R20 定稿；每条可追溯到 01 事实清单或 GOLDEN；选定 3–4 条待裁决口径 |
| 2 | 定契约 Schema + 讲师系统参考适配 | 参考适配 L3 达到全部核对通过；适配无状态，重启后结果不变；适配内无业务计算 |
| 3 | 导出剧本 L1/L2/L3 | 剧本中不出现讲师系统的表名、路径、枚举值；每条资金规则至少被 1 个期望值覆盖；对任一事件做扰动至少一个期望值变化（无死事件） |
| 4 | 写验收器 `accept.py` | 报告按规则编号定位；冒烟、分层、重启、自检反例均可用；复用 `check_report.py` 的防伪思路 |
| 5 | 错误实现检验 | 准备「归属给最后跟进人」「B 级额度每月重置」等似是而非的错误实现，必须被判失败且报告指向正确规则编号 |
| 6 | 异构试点 | 用另一种技术栈从零快速实现一版（可由 AI 生成），验证「换实现也能接上、也能测出错误」，记录适配实际行数与接入耗时 |

## 10. 已知边界与风险

- **金额与时间口径**：统一整数元（或分）比较；月末、时区、「当日」截止时刻写入规则卡。
- **功能范围不同**：`UNSUPPORTED` 不计分但在报告中列出，评分时另行考虑范围。
- **口径申诉**：学员发现规则卡歧义时，经讲师裁决后更新规则卡与期望值并发布新版本号。
- **评分偏向资金**：自动验收只证明「钱算对」；页面交互、权限体验、视觉仍需人工检查项托底。
- **运行环境**：学员系统需提供一键启动（如 docker-compose），否则验收器无法在隔离环境运行。
- **验收器不能证明的事**：真实上游兼容性、并发容量、真实第三方服务（OCR 等）仍需学员另行演示证据，与现有 CASES「当前尚未证明」一致。
